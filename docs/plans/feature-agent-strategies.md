# План ветки `feature/agent-strategies` (P4, @egrsid)

> Копия плана из `CLAUDE.md` ветки. Ниже, в разделе «Статус выполнения», — что сделано, как проверить и известные ограничения.

## 1. Цель и границы

**Цель ветки:** дать агенту две стратегии сверх «LLM придумала признак»:
1. **Анализ худших объектов** — где текущая лучшая модель ошибается (сегменты признаков, края таргета, классы и
   путаница); короткая сводка уходит планировщику, чтобы гипотезы били в реальные слабые места.
2. **Подбор гиперпараметров как стратегия** — вид гипотезы `tune`: агент без кодера вызывает `tuning.tune` (P1) на
   признаках текущего лучшего кода, оценивает найденное обычным правилом принятия и фиксирует параметры в `PARAMS`.

**Входит в ветку:**
- `error_analysis.py` — новый плоский модуль P4 (stdlib + numpy/pandas), без вызовов LLM.
- Проводка в `agent.py`, вид `tune` и секция «где ошибается модель» в `prompts_agent.py`.
- `StubTuner` в `tests/mocks.py`, тесты `tests/test_agent_errors.py`, `tests/test_agent_tune.py`.
- `docs/plans/feature-agent-strategies.md` — первым коммитом.

**Не входит:** сам подбор (Optuna, пространства поиска, прунинг) — `tuning.py`, зона P1. Для разработки создана
ветка-заглушка `stub/p1-tuning` (только контракт и подбор-пустышка, не мержить). Target-encoding внутри фолда — P1.

## 2. Контракты

```python
# error_analysis.py (P4)
analyze_errors(x: DataFrame, y, oof, task_type: str, *, classes=None, cat_cols=(), max_chars=800,
               max_columns=40, min_segment=30) -> str      # "" если анализ невозможен (нет oof, не та форма)

# tuning.py (P1; заглушка — ветка stub/p1-tuning)
tune(spec, build_features, cfg: {"model", "params", "target_transform", "n_trials", "seed"}, deadline) -> dict
```

- `oof`: регрессия — вектор предсказаний в сырых единицах; классификация — вероятности `(n, k)`, столбцы в порядке
  `Candidate.meta["classes"]`, а если его нет — отсортированных строковых меток (как у `StubEvaluator`).
- В анализ идут исходные признаки (`TaskData.train_x`) и таргет — оба уже есть в процессе харнесса; в промпт
  попадают только агрегаты по сегментам, не строки. В песочницу LLM-кода таргет по-прежнему не попадает.

## 3. Анализ худших объектов (`error_analysis.py`)

- Ошибка на объекте: регрессия — `|y − oof|`; классификация — `1 − p(истинный класс)`.
- Концентрация: «10% худших объектов дают X% суммарной ошибки» (регрессия — по квадрату ошибки).
- Сегменты: категориальные — уровни (≤ 20 самых частых), числовые — 5 квантильных корзин, пропуски — отдельный
  сегмент. Сегмент учитывается при размере ≥ `max(min_segment, 0.5% n)`. Ранжирование по вкладу
  `(средняя ошибка сегмента − общая) × размер`; в сводку — топ-6: `facility_type=Data_Center (n=120): error 4.1× avg`.
- Регрессия: смещение по квантилям таргета (`y top 10%: mean residual −45, underpredicted`).
- Классификация: recall по классам (3 худших), топ-3 пары путаницы `Exploits→DoS (1234)`.
- Время: ≤ ~2 с на public-объёмах (векторно, без циклов по строкам); при любой ошибке — `""`, агент не падает.

## 4. Подбор как стратегия (вид `tune`)

- Планировщику вид `tune` предлагается, только если `tuning.tune` доступен (реальный модуль или переданный
  в `research(..., tuner=...)`); иначе гипотезы `tune` отбрасываются при разборе плана.
- Исполнение: признаки базового кода в песочнице → `tune(spec, build_features, cfg, sub_deadline)` с бюджетом
  `min(tune_seconds, tune_share · остаток окна)` → нормализация по белому списку `MODEL_PARAMS` →
  `evaluate` → `decide`. Новый код = базовый с заменённым литералом `PARAMS` (воспроизводимо, кумулятивно).
- Авто-подбор: если сработал бы стоп по плато, подбора ещё не было и время есть — один раз выполнить `tune`.
- Ошибка/таймаут подбора → эксперимент `failed` с причиной, цикл идёт дальше.

## 5. План работ по шагам (порядок не перескакивать)

Каждый шаг — отдельный маленький коммит (`feat|fix|test|docs|refactor: что сделано`).

0. `docs/plans/feature-agent-strategies.md` — первым коммитом (копия разделов 1–8).
1. `error_analysis.py` + тесты на синтетике с заложенным «плохим» сегментом (регрессия, бинарная, мультикласс),
   инвариант длины, устойчивость к мусору (NaN, одна категория, неверная форма oof).
2. Проводка анализа: после эталона и каждого принятого кандидата — пересчёт; секция в промпте планировщика;
   тест «секция есть в re-plan»; бюджет промпта ≤ 4k токенов.
3. Вид `tune`: `StubTuner` в моках, замена `PARAMS` в коде, исполнение, нормализация, авто-подбор на плато;
   тесты: принят/отклонён/упал/нет тюнера/таймаут.
4. Замер: размер промптов, время анализа на public-задачах, dry-run обеих задач.
5. Живой прогон Qwen (≤ 3 итераций, мультикласс): использует ли планировщик сводку ошибок; токены.
6. Статус в `docs/plans/feature-agent-strategies.md` и `CLAUDE.md`.

## 7. Definition of Done

- Все прежние тесты зелёные; без `tuning` и при сбое анализа агент ведёт себя как раньше.
- Сводка ошибок ≤ `max_chars`, без строк данных; на синтетике заложенный плохой сегмент — первый в списке.
- `tune`: принятый подбор даёт кандидата с `PARAMS` в `meta["code"]`, следующий эксперимент строится на нём.
- Промпт планировщика с секцией ошибок и памятью на 30 экспериментов ≤ 4k токенов.
- `error_analysis.py` импортируется без модулей команды; только stdlib + numpy/pandas.

## 8. Риски

| Риск | Мера |
|---|---|
| Сводка ошибок «подсказывает» таргет и LLM подгоняет под CV | только агрегаты по сегментам из OOF; правило принятия и порог шума те же |
| Анализ медленный на больших данных | ≤ 40 колонок, векторно, корзины по квантилям; тест времени на public |
| Подбор съедает окно research | бюджет `min(tune_seconds, tune_share · остаток)`, deadline передаётся в `tune` |
| Контракт `tune` разойдётся с P1 | заглушка-контракт в `stub/p1-tuning`, адаптер `_optional("tuning", "tune")` |
