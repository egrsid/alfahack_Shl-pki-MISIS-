# Проект: хакатон Альфа-Банк × Changellenge — «AI-агент для разработки ML-моделей» (трек AutoML)

> Этот файл относится к ветке `feature/agent-loop` (роль P4, владелец — @egrsid).
> Общий план команды (5 человек, роли, этапы, Git-процесс) живёт в `main`; здесь он сведён к тому, что нужно для работы над циклом агента.

## Суть проекта
Универсальный LLM-управляемый агент получает текстовое описание ML-задачи и CSV-файлы
(`train.csv`, `test.csv`, `data_dictionary.csv`, `sample_submission.csv`) и сам: анализирует данные, определяет тип задачи,
пишет и запускает код, обучает модель, валидирует, формирует файл предсказаний.
Сдаётся КОД агента (ZIP с `solution.py` в корне), а не модель. Платформа запускает его на разных задачах.

## Оценка
- Public: 2 известные задачи.
  1. Регрессия — годовое удельное энергопотребление зданий (`site_eui`), метрика RMSE. train 53 308 × 64, test 22 449 × 63.
  2. Мультикласс — тип кибератаки (`attack_cat`), основная метрика Macro F1. train 87 670 × 44, test 41 166 × 43.
- Private: 2 скрытые новые задачи (метрики и содержание не раскрыты). Берётся сабмит с лучшим public score, код не меняется.
- Баллы нормируются относительно бейзлайна (хуже или равно бейзлайну → 0):

$$S_{reg} = 100 \cdot \max\left(0,\; 1 - \frac{RMSE}{B_{RMSE}}\right), \qquad
S_{cls} = 100 \cdot \max\left(0,\; \frac{MacroF1 - B_{F1}}{1 - B_{F1}}\right)$$

$$Score = \frac{S_1 + S_2}{2}$$

Главное: надёжность и универсальность на НЕЗНАКОМЫХ задачах, а не подгонка под public.

# Ветка `feature/agent-loop` — AutoResearch-агент (P4)

## 1. Цель и границы

**Цель ветки:** `agent.research(spec, best, llm, deadline) -> list[Candidate]` — работающий LLM-управляемый цикл
«гипотеза → код → песочница → оценка харнессом → решение → следующая итерация», который при работающих соседних модулях улучшает CV лучшего
fallback-кандидата, а при любом сбое (LLM, песочница, мусорный код) возвращает то, что есть, и не роняет процесс.

**Входит в ветку:**
- `agent.py` — цикл, парсинг ответов LLM, запуск эксперимента, правило принятия, стоп-критерии, обработка ошибок.
- `prompts_agent.py` — промпты ролей (аналитик → генератор гипотез → кодер → критик) и шаблоны ответа.
- `memory.py` — **минимальная** версия журнала (список экспериментов + сводка для промпта + дамп в JSONL). Полноценное сжатие/дедупликация — ветка `feature/experiment-memory`.
- Тесты агента на моках (`tests/test_agent*.py`, `tests/mocks.py`; вне ZIP, согласовать с P5).
- `docs/plans/feature-agent-loop.md` — первым коммитом (копия плана ниже + раздел «что сделано / как проверить / ограничения» по мере работы).

**Не входит** (чужие модули, не трогать без PR к владельцу): `solution.py`, `schemas.py`, `budget.py`, `evaluator.py`, `eda.py`, `tuning.py`, `ensemble.py` (P1);
`llm_client.py`, `task_understanding.py` (P2); `fallback.py`, `preprocess.py`, `metrics.py`, `submission.py` (P3); `sandbox.py`, `guards.py` (P5).
Позже и отдельными ветками: optuna-стратегии, анализ худших объектов (`feature/agent-strategies`), добавление найденных признаков в ансамбль (P1).

**Агент НИКОГДА не пишет `submission.csv`** — он возвращает `Candidate`-ы. Запись делает `solution.py` через `submission.write` и только при улучшении CV.

## 2. Контракты и зависимости

Что агент получает и отдаёт (из `schemas.py`, замораживаются P1; менять — только через PR с согласием всех):

```python
research(spec: TaskSpec, best: Candidate, llm: LLMClient | None, deadline: Deadline) -> list[Candidate]
# возвращает принятые кандидаты по убыванию CV (первый — лучший), oof/test_pred в «сырых» единицах;
# в Candidate.meta: {"code": <исходник build_features>, "model": ..., "params": ..., "hypothesis": ..., "iter": n}
```

Зависимости и чем заменяем, пока ветка соседа не смержена. Все внешние модули импортируются **через тонкие адаптеры** внутри `agent.py` (`try/except ImportError`, `typing.Protocol`), чтобы `agent.py` импортировался и тестировался без них:

| Что нужно | Владелец | Интерфейс | Заглушка в моей ветке |
|---|---|---|---|
| LLM | P2 | `llm.chat(messages, **kw) -> str`, `llm.chat_json(messages, schema) -> dict`; `LLMUnavailable` | `MockLLM` — отдаёт заранее заданные ответы по сценарию |
| Оценка | P1 | `evaluator.evaluate(spec, build_features, params, deadline) -> Candidate` | `StubEvaluator`: 5-fold LightGBM, фиксированный сид, метрика из `metrics`/`sklearn` |
| Песочница | P5 | `sandbox.run_code(code, cwd, timeout) -> ExecResult(stdout, stderr, returncode, artifacts)` | `subprocess.run([sys.executable, "-I", ...], env={чистый}, timeout=...)` |
| Профиль данных | P1 | `eda.profile(train, test, spec) -> dict` (≤ 2–3 тыс. токенов) | `_mini_profile()` в `agent.py` (типы, пропуски, кардинальность, таргет) |
| Дедлайн | P1 | `deadline.left()`, `deadline.stage("research")` | `SimpleDeadline(seconds)` в моках |
| Защита | P5 | `guards.check_candidate(spec, cand, baseline) -> list[str]` | no-op, вызов за флагом |

Заглушки лежат в `tests/mocks.py` (вне ZIP). Когда сосед мержится — адаптер подхватывает реальный модуль, заглушка остаётся для тестов.

## 3. Архитектура цикла

```
research(spec, best, llm, deadline)
│
├─ 0. preflight: llm is None / LLM_DISABLED=1 / deadline мал  →  return []
├─ 1. context: профиль данных (eda.profile) + spec.feature_notes + метрика/направление  → компактный текст ≤ ~3 тыс. токенов
├─ 2. plan:    LLM(analyst+planner) → JSON со списком гипотез, отсортированных по ожидаемому выигрышу/стоимости
│  └─ очередь гипотез; пополняется (re-plan с учётом памяти), когда пуста
└─ цикл по гипотезам, пока не сработал стоп:
     3. code:     LLM(coder) → блок ```python по фиксированному шаблону (база = код текущего лучшего → эксперименты кумулятивные)
     4. validate: compile() + быстрые статические проверки (запрещённые импорты/вызовы), без исполнения
     5. run:      песочница строит признаки → parquet; харнесс проверяет форму и качество признаков
     6. evaluate: evaluator.evaluate на ТЕХ ЖЕ сплитах и сиде, что у best → Candidate
     7. decide:   принять, если улучшение > порога шума CV; иначе откатить
     8. record:   запись в memory (гипотеза, код-дифф, cv, время, ошибка, токены)
     9. (опц.) critic: короткий разбор 1–2 последних отклонённых — только если остался токен-бюджет
```

Ключевые решения:
- **Жадное накопление.** Принятая гипотеза становится базой для следующего эксперимента (код лучшего передаётся кодеру). Отклонённая — не влияет на базу, но остаётся в памяти («не повторять»).
- **Одна гипотеза = одно изменение.** Иначе непонятно, что дало эффект, а критик/память теряют смысл. Исключение — первая итерация «базовая подготовка» (даты, строки, пропуски), если fallback её не покрыл.
- **Re-plan по пустой очереди**, а не каждую итерацию: экономит токены (один дорогой вызов на 6–8 гипотез).
- **Текстовый протокол как основной.** JSON для плана, ```python для кода; нативный tool-calling Qwen не используем как единственный путь (в `<think>…</think>` и «болтовне» вокруг ответа нужно уметь вырезать нужное сами).

## 4. Протокол эксперимента (что именно пишет LLM и как это исполняется)

**Шаблон ответа кодера** (единственное, что принимается):

```python
import numpy as np
import pandas as pd

def build_features(train: pd.DataFrame, test: pd.DataFrame, spec: dict) -> tuple[pd.DataFrame, pd.DataFrame]:
    """Вернуть (X_train, X_test) с теми же строками и в том же порядке. Без таргета."""
    ...

MODEL = "lightgbm"     # опц.: "lightgbm" | "catboost" | "xgboost"
PARAMS = {...}         # опц.: гиперпараметры модели (только из белого списка ключей)
TARGET_TRANSFORM = None  # опц.: None | "log1p" (только регрессия)
```

**Исполнение (защита от «обмана метрики»):**
1. Харнесс (наш код) пишет в каталог эксперимента `.agent_work/exp_<n>/` (подкаталог задачи; промежуточные файлы там разрешены) файлы `train_X.parquet`, `test_X.parquet`:
   **признаки без таргета, без id и без `spec.drop_cols`**. Таргет в песочницу не попадает вообще → target-encoding и утечку через таргет сделать нельзя по построению.
2. Наш раннер (не LLM-код) импортирует присланный `build_features`, вызывает, пишет `feat_train.parquet`, `feat_test.parquet`. Процесс — через `sandbox.run_code` с таймаутом (по умолчанию 300 с на построение признаков), чистый `env` (никаких `OPENAI_*`), результат — только через файлы, не через stdout.
3. Харнесс валидирует выход: те же число строк и порядок, нет таргета/id, нет inf, NaN допустимы (бустинг их ест), колонок ≤ 2000, object-колонки приводятся к `category`, одинаковый набор колонок и dtype в train/test.
4. Метрику, CV-сплиты и обучение выполняет `evaluator.evaluate` по зафиксированному сиду. LLM-код возвращает только признаки / `PARAMS` / `MODEL`. Код LLM метрику не считает и не видит `submission.csv`, сплитов, test-таргета.
5. Подозрительно «чудесный» скачок (например, > N·σ шума или кривая CV резко выше fallback) → не принимать сразу, а перепроверить (`guards.check_candidate`, повторный прогон с другим сидом сплита, если есть бюджет).

Ограничение шаблона: нужен target-encoding или другая target-зависимая обработка → отдельная фаза позже (энкодеры внутри фолда в харнессе у P1, агент выбирает их по имени). В этой ветке не делаем.

## 5. LLM-протокол и промпты (`prompts_agent.py`)

- Роли — разные системные промпты одного агента: **analyst** (читает профиль → выводы о данных), **planner** (гипотезы), **coder** (код по шаблону), **critic** (разбор отклонений/ошибок, опционально).
- Ответы:
  - planner: `chat_json` со схемой `{"hypotheses": [{"id", "title", "kind", "rationale", "expected_gain": "low|mid|high", "cost": "low|mid|high"}]}`,
    `kind ∈ {features, encoding, missing, outliers, target_transform, params, model, feature_selection}`; максимум 8 штук, без дублей с памятью.
  - coder: один блок ```python```; всё вне блока игнорируем; 1 попытка «починить» формат (если блока нет) + 1 попытка ремонта по traceback.
  - critic (по желанию): ≤ 120 слов, формат «что не сработало → что попробовать вместо».
- Язык промптов: стартуем с английского для инструкций кода/формата (меньше сбоев у Qwen на структурированном выводе) и русского/исходного для описания задачи и `feature_notes`; A/B на 2–3 прогонах и фиксируем выбор в `docs/plans/feature-agent-loop.md`.
- Few-shot: 1 короткий пример валидного ответа coder и planner в каждом промпте — формат важнее «умности».
- Qwen может выдавать рассуждения (`<think>…</think>`): вырезать при парсинге, выставлять `max_tokens` (план ≤ ~1.2k, код ≤ ~1.5k), температура низкая для кода (≈0.2) и выше для плана (≈0.7).
- В промпт попадают **сводки, не данные**: профиль, имена колонок с заметками, сжатая память (последние ~8 экспериментов + список «уже пробовали / не помогло»), код текущего лучшего. Сырые строки датафрейма — никогда.
- Бюджет промпта: ориентир ≤ 4k токенов вход + ≤ 1.5k выход на итерацию → цикл на 12 итераций ≈ 70–100k токенов. Реальный расход измерить в шаге 8 и записать в план (цены в ₽ не выдумываем — берём фактический счётчик из `llm_client`).

## 6. Решение «принять / отклонить»

- Направление берём из `spec.greater_is_better`; `gain = new - best` (если больше — лучше) или `best - new`.
- **Принимаем**, если `gain > ACCEPT_K * noise`, где `noise = best.cv_std / sqrt(n_folds)` (стандартная ошибка по фолдам), `ACCEPT_K = 1.0` стартово.
  Если `evaluate` отдаёт `meta["fold_scores"]` — используем парную разность по фолдам (честнее, т.к. сплиты одинаковые).
- Дополнительно минимальный относительный порог `MIN_REL_GAIN` (напр. 0.0005 · |best|), чтобы не принимать «шум в пределах точности».
- Константы вынесены в `AgentConfig` (dataclass) — калибруем на public-задачах: сколько «выигрышей» на повторном прогоне baseline с другим сидом (должно быть ≈ 0).
- Агент не видит hold-out, который P1 держит для финальной проверки на переобучение под CV (множество гипотез → оптимистичный CV). Задача агента — не раздувать число принятых мелких «улучшений» (отсюда порог шума).

## 7. Бюджеты и стоп-критерии

Все числа — в `AgentConfig`, времена берём из `Deadline`, не хардкодим.

| Что | Значение по умолчанию | Откуда |
|---|---|---|
| Остановка исследования | `deadline.stage("research")` (≈ T+2ч05) | P1 `budget.py` |
| Таймаут построения признаков | 300 с | `AgentConfig` |
| Таймаут `evaluate` одного кандидата | min(900 с, остаток до «research») | `AgentConfig` + `Deadline` |
| Макс. итераций | 12 (поднять после замера стоимости) | `AgentConfig` |
| Макс. токенов на задачу | задаётся счётчиком P1/P2; агент останавливается при превышении своей доли | `llm_client` |
| Подряд неудач (ошибка кода/формата) | 3 → стоп | CLAUDE: «3 неудачи подряд» |
| Подряд без улучшений | 5 → стоп (плато) | `AgentConfig` |
| `LLMUnavailable` / `Budget has been exceeded` | стоп немедленно, вернуть накопленное | P2 |

Порядок проверок перед каждой итерацией: время → токены → LLM жив → очередь гипотез. Запас на финальное обучение/ансамбль — не наша зона, но агент **не тратит последние минуты окна `research` на новый эксперимент**, если ожидаемая длительность не помещается.

## 8. Обработка ошибок (агент не падает ни при каких входах)

- Весь `research` обёрнут в `try/except Exception` на верхнем уровне: при сбое — вернуть `[]` либо уже накопленных кандидатов, залогировать причину. (`solution.py` у P1 тоже оборачивает вызов — двойная защита.)
- Ошибка LLM-кода: traceback обрезается (≤ 1500 символов, хвост) и уходит в **одну** попытку ремонта; повторная ошибка → гипотеза помечается `failed`, идём дальше.
- Таймаут/OOM в песочнице → гипотеза `failed`, процесс убит вместе с деревом (на стороне P5), в память пишем «слишком тяжёлая».
- Невалидный JSON/нет блока кода → 1 попытка «починить формат»; иначе пропуск.
- Валидация выхода признаков провалилась (строки/таргет/NaN-лавина/взрыв колонок) → `failed` с текстом причины в память — кодер увидит и не повторит.
- Кэш LLM-ответов (дисковый, у P2) должен работать и для повторных запусков при отладке — лишние токены не жжём.

## 9. Память экспериментов (`memory.py`, минимальная версия)

- `Experiment`: `id, hypothesis, kind, status ∈ {accepted, rejected, failed}, cv_score, cv_std, gain, code_hash, error, duration_s, tokens_in/out, ts`.
- `ExperimentMemory.add()`, `.summary(max_chars) -> str` (для промпта: что принято, что отклонено и почему, что падало), `.dump_jsonl(path)` (в `.agent_work/`, для отладки).
- Для планировщика — список `tried_titles/kinds`, чтобы не предлагать дубли.
- Сжатие, ранжирование «что ещё не пробовали», дифф кода — в `feature/experiment-memory`.

## 13. Риски ветки и что с ними делать

| Риск | Мера |
|---|---|
| Qwen ломает формат (нет блока, JSON с комментариями, `<think>`) | жёсткий парсер, 1 попытка починки, пропуск гипотезы, few-shot в промптах |
| Токены/₽ (бюджет общий на команду) | сводки вместо данных, короткие ответы, кэш, живые прогоны редко и с `max_iters=3`, счётчик в логе |
| Переобучение под CV из-за множества гипотез | фиксированные сплиты и сид, порог шума, hold-out у P1, ограничение числа принятых шагов |
| Утечка через LLM-код | таргет не передаётся в песочницу, метрику считает харнесс, `guards.check_candidate` (P5) |
| Тяжёлые признаки (OOM / слишком долго) | таймаут и лимит колонок, пометка «тяжело» в памяти, проверка на объёме public-данных |
| Агент «обманывает» шум: берёт случайные выигрыши | порог по SE фолдов, калибровка `ACCEPT_K` повторным прогоном baseline с другим сидом |
| Универсальность: скрытые задачи другого типа (бинарная/AUC, MAE, строки, даты) | промпты берут тип/метрику/направление из `spec`, а не из текста public; тесты на датасетах P5 |
| Расхождение контрактов с P1/P2/P5 | см. открытые вопросы ниже; адаптеры локализуют изменения в одном месте |

## 14. Открытые вопросы к владельцам смежных модулей

- **P1 (`evaluator.evaluate`):** принимает ли он callable `build_features` или готовые признаки? Агент хочет передавать «готовые train/test-признаки + `model/params/target_transform`» (код LLM исполняется в песочнице, не в процессе харнесса). Нужны `Candidate.meta["fold_scores"]` и поддержка `target_transform="log1p"`.
- **P1 (`Deadline`, токены):** как агент узнаёт остаток токенов/₽ и долю, отведённую на research? Какой `stage` брать для таймаута `evaluate`?
- **P2 (`llm_client`):** сигнатуры `chat`/`chat_json`, `max_tokens`/`temperature` в `**kw`, как отдаются счётчики токенов, вырезает ли клиент `<think>`, кэш по хешу сообщений.
- **P5 (`sandbox`):** `run_code` принимает код строкой или путь? Можно ли передать `cwd` в `.agent_work/exp_<n>/` и получить `artifacts`; лимит памяти; что `guards.check_candidate` проверяет сверх того, что делаем мы.
- **P3 (`metrics`):** ключи метрик и направление — агент использует их только через `spec`.

## 15. Общие рабочие правила для кода

- Любой вызов LLM: таймаут, ограниченное число ретраев, логирование токенов, аккуратная обработка `Budget has been exceeded`; при отказе LLM агент завершается и возвращает накопленное.
- Код, сгенерированный LLM, исполняется в отдельном процессе с таймаутом; его выводу не доверяем без проверки харнессом.
- Ничего не скачивать из интернета и не вызывать `pip` из кода. Абсолютные пути к своей машине в код не писать.
- Ветка `feature/agent-loop` от свежего `main`, живёт 1–2 дня; мелкие PR лучше больших. Файлы других владельцев правим только через PR к ним/с их согласия. `solution.py` и `schemas.py` — только P1.
- Не коммитить: `.env`, ключи, данные (`*.csv`), `*.zip`, `.venv`, `.llm_cache/`, `.agent_work/`.
- Сообщение в чат команды при мердже: что изменилось и нужно ли `git pull --rebase`.
